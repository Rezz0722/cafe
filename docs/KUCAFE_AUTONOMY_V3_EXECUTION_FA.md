# دفتر کار خودکار کو کافه — برنامهٔ اجرایی نسخهٔ ۳

تاریخ مبنا: ۱۸ مهر ۱۴۰۵. این سند برنامه و معیار پذیرش است، نه ادعای تکمیل. وضعیت واقعی هر قابلیت فقط از رویداد، checkpoint، PR، CI و SHA منتشرشده تعیین می‌شود.

## وضعیت واقعی در شروع

- زمان‌بند و کنترلر مستقل از این گفت‌وگو اجرا می‌شوند؛ دو کار محدود کدنویسی مصوب قبلی تکمیل شده‌اند. خالی‌بودن صف به معنی پیشرفت پروژه نیست.
- داشبورد عمومی از snapshot و رویدادهای واقعی هر ۱۵ ثانیه تازه می‌شود. کنسول `/admin/autonomy` با نشست مدیر پیام می‌گیرد و پاسخِ عاملِ فقط‌خواندنی را بعد از چرخهٔ بعدی نشان می‌دهد. این هنوز مکالمهٔ پیوسته یا فرمان توسعه نیست.
- مدلِ کدنویسی فقط در محدودهٔ roadmap نسخه‌دار می‌تواند پیشنهاد patch بدهد. کنترلر بازبینی، CI، ادغام عادی و انتشار SHA دقیق را کنترل می‌کند. تحقیق کنونی برای ۱۷ پرونده، فاقد شاهد مثبتِ معتبر بود؛ نباید آن را ورود داده به سایت نامید.
- آزمون با حساب واقعی مدیر و یک درخواست جدید تا انتشار کامل انجام نشده است. هیچ کدام از این موارد را «۱۰۰٪ عملیاتی» برچسب نزن.

گام پیاده‌سازی جاری: جریان JSONL عامل به برچسب‌های ثابت و بدون متن/فرمان تقلیل می‌یابد تا در اجرای چنددقیقه‌ای، «تحلیل/جست‌وجو/آماده‌سازی خروجی» واقعاً به‌روزرسانی شود. این تغییر به‌تنهایی درخواست تازه را وارد صف توسعه نمی‌کند.

## اصول تصمیم‌گیری

۱. GitHub مسیر یگانهٔ تغییر محصول و کنترلر است: branch → PR → CI → merge محافظت‌شده → deploy → smoke. متن در کنسول هرگز مستقیم روی Production اجرا نمی‌شود.
۲. هر درخواست مالک شناسهٔ پایدار، نوع، وضعیت، طرح، شواهد، محدودهٔ فایل، معیار پذیرش، ریسک، نتیجهٔ تست، PR و SHA انتشار دارد. میان «ثبت شد»، «برنامه‌ریزی شد»، «در اجراست» و «منتشر شد» تفاوت صریح است.
۳. کارهای کم‌ریسک، کوچک و برگشت‌پذیر پس از اعتبارسنجی ماشینی و بازبینی مستقل می‌توانند خودکار پیش بروند. migration، حذف/ویرایش دادهٔ واقعی، پیامک/هزینه، تغییر auth/secret، زیرساخت و عملیات مشتری نیازمند توقف و تصمیم جدا هستند؛ مجوز کلی استفاده از سرور جای تحلیل ریسک هر عمل را نمی‌گیرد.
۴. تحقیق اینترنتی فقط با URL، تاریخ، هویت شعبه و ادعای قابل‌ردیابی وارد طرح می‌شود. فقدان شاهد یعنی «نامعلوم»، نه دسته‌بندی ساختگی.
۵. سهمیهٔ مدل، کمبود دیسک، قطع GitHub، خطای CI یا انتشار، نبود داده و توقف کاربر حالت‌های عادی سیستم‌اند؛ checkpoint و retry محدود باید از تکرار عملیات خارجی جلوگیری کند.

## فاز ۰ — خط مبنا و قابلیت بازیابی

خروجی: فهرست نسخهٔ فعال اپ/کنترلر، وضعیت timer و runner، فضای دیسک، نقاط backup و روش rollback ثبت شود. تست: خاموش/روشن‌کردن کنترلر بدون تغییر دیتابیس، خواندن checkpoint، تأیید SHA دقیق و عدم تداخل با deploy. معیار خروج: هیچ «کار فعال» صرفاً از روشن‌بودن timer استنتاج نشود.

## فاز ۱ — ثبت رویداد و کنسول واقعاً زنده

خروجی: event journal پایدار و محدود با `requestId/taskId`, مرحله، زمان، مدت، دلیل توقف و لینک‌های معتبر PR/CI/deploy؛ UI مدیر با تازه‌سازی پیوسته یا stream کوتاه‌عمر و fallback polling، تشخیص stale، جست‌وجو/فیلتر رخدادها و نمایش جزئیات هر کار. رویداد خام مدل، secret و متن خصوصی به داشبورد عمومی نرود. معیار خروج: رویدادهای یک چرخهٔ واقعی، خطا و retry بدون دستکاری دستی در UI دیده شوند؛ قطع اتصال و stale با «در حال کار» اشتباه نشوند.

## فاز ۲ — درخواست تعاملی و برنامه‌ریز محدود

خروجی: پیام مدیر به ticket تبدیل شود؛ سؤال، درخواست تحقیق، تغییر محصول و عملیات از هم تفکیک شوند. برنامه‌ریز با شواهد مخزن/محصول، taskهای کوچک، فایل‌های مجاز، تست، smoke، وابستگی و rollback پیشنهاد دهد. validator قطعی اجازهٔ ساخت task فقط در مسیرها و بودجهٔ تغییرِ مجاز را بدهد؛ درخواست مبهم یا حساس در وضعیت «نیازمند داده/تصمیم» بماند. پذیرش درخواست نباید وانمود کند اجرای آن شروع شده. معیار خروج: یک درخواست کم‌ریسک از کنسول تا task قابل‌ردیابی پیش برود؛ درخواست migration/حذف داده بی‌صدا اجرا نشود.

گام جاری: نوع «سؤال/درخواست توسعه»، طرح محدود یک‌تسکی، بازبینی مستقل، صف خصوصی قفل‌شده با hash و نمایش وضعیت در UI پیاده‌سازی می‌شود. این دامنه عمداً تحقیق اینترنتی پویا، تغییرات حساس و درخواست بسیار کلی را خودکار اجرا نمی‌کند. معیار end-to-end فاز فقط بعد از تست درخواست واقعی مدیر تا انتشار همان SHA محقق است.

## فاز ۳ — تحقیق و مدیریت شواهد

خروجی: پژوهش وبِ محدود و تاریخ‌دار، تطبیق شعبه، ثبت منبع مستقیم، بازبین مستقل و dossier قابل دانلود؛ طرح توسعه بتواند به شواهد پژوهش لینک دهد. نتیجهٔ صفر شاهد معتبر هم نتیجهٔ درست است. معیار خروج: نمونهٔ دارای شاهد و نمونهٔ بی‌شاهد هر دو با منبع، تاریخ و تصمیم درست نشان داده شوند؛ محتوای وب اختیار فرمان‌دادن ندارد.

## فاز ۴ — اجرای خودکار امن از GitHub

خروجی: taskهای مجاز به planner → writer → reviewer → patch validator → PR → hosted CI → merge محافظت‌شده → deploy → live smoke متصل شوند. یک task در هر زمان، قفل و checkpoint اتمیک، سقف تلاش، branch/commit idempotent و وابستگی به SHA دقیق لازم است. معیار خروج: حداقل یک تغییر واقعیِ کم‌ریسک، از ticket مدیر تا Production، با PR/تست/SHA و rollback مشخص؛ شکست CI یا deploy با برچسب واضح بماند.

## فاز ۵ — پایش، کنترل و دوام عملیاتی

خروجی: health check مستقل timer/runner/app، هشدار توقف طولانی یا stale، صف خطا، pause/resume و retry کنترل‌شده از UI مدیر، محدودیت نرخ/دیسک/سهمیه، history قابل‌بازیابی و گزارش روزانهٔ «چه تغییر کرد/چه نشد/چرا». فرمان‌های حساس در UI باید نقش‌محور، CSRF-safe و ثبت‌شده باشند. معیار خروج: سناریوهای quota، قطعی GitHub، تمام‌شدن دیسک، شکست build، rollback و ریستارت سرور در تست بدون ادعای موفقیت کاذب مدیریت شوند.

## معیار نهایی «دفتر کار عملیاتی»

تا وقتی این زنجیره با حساب مدیر واقعی و یک درخواست تازه end-to-end تکرارپذیر آزمایش نشده، سیستم کامل اعلام نمی‌شود: `ثبت درخواست → طرح با شواهد و مرز ریسک → تحقیق لازم → کد/بازبینی → PR/CI → انتشار SHA دقیق → smoke → گزارش و پاسخ در UI`. برای عملیات حساس، خروجیِ درست ممکن است توقفِ مستند به‌جای اجرای بی‌اجازه باشد. تضمین توسعهٔ نامحدود، رشد رتبه، یا نتیجهٔ کسب‌وکار از این سامانه ممکن نیست.

## مسئولیت‌های عملیاتی

- مالک: ورود با حساب مدیر برای آزمون واقعی کنسول؛ اطلاعات/تصمیم‌هایی که فقط خود او دارد، مانند قرارداد مشتری یا نتیجهٔ پایلوت.
- کنترلر: لاگِ بدون راز، تصمیم ریسک، checkpoint، orchestration و GitHub-only deploy.
- CI/CD: تست، typecheck، build و نشر محافظت‌شده.
- UI: نمایش وضعیت و شواهد واقعی؛ هر status با زمان و منبع، نه متن تبلیغاتی.

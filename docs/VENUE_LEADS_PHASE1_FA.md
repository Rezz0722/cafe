# فاز ۱ — درخواست و تحویل پنل کافه‌دار

## قرارداد محصول و مرز دسترسی

صفحه اصلی → `/for-cafes?from=home` → درخواست بدون ورود و با رضایت تماس → رسید → `/profile/venue-requests` با شمارهٔ تأییدشده → انتخاب دقیق شعبه و `place_claim` در وضعیت pending → بررسی انسانی ادمین در `/admin/leads` → فعال‌سازی اتمیک نقش همان شعبه → پنل فعلی `/admin/venue`.

فرم فروش از `place_submission` مستقل است. کافهٔ تازه از مسیر موجود ثبت/بازبینی کافه عبور می‌کند؛ این فرم مکان تازه یا کاربر تازه ایجاد نمی‌کند. تأیید شماره، تأیید مالکیت نیست. بدون OTP تأییدشده، اتصال یا خواندن درخواست صرفاً با دانستن شماره ممنوع است. آزمون محلی با حساب/نشست fixture، تحویل SMS واقعی را ثابت نمی‌کند.

## ذخیره و امنیت

- فقط دو جدول افزایشی: `venue_lead` و bucket نرخ `venue_lead_rate`؛ claims، roles، تنظیمات تماس و `audit_log` موجود استفاده می‌شوند. Migration شماره 0013 با collation پیش‌فرض همان دیتابیس اجرا می‌شود تا FKهای UUID با `app_user` سازگار بمانند. این موضوع روی CI MariaDB 11.4 و دیتابیس production خواندنی بررسی شد.
- فرم کوتاه: نام، موبایل، کافه، شهر، شعبهٔ اختیاری. source فقط home/cafe/direct است؛ referrer یا query خام ذخیره نمی‌شود. رضایت صرفاً برای پاسخ درخواست است، نه بازاریابی.
- کد پیگیری تصادفی 96-bit، صرفاً reference است؛ endpoint عمومی جست‌وجوی شماره/کد و اطلاعات خصوصی وجود ندارد. با request-key تصادفی 128-bit همان فرم، retry رسید خود را می‌گیرد؛ فرم دیگر برای درخواست مشابه، کد قدیمی را دریافت نمی‌کند.
- uniqueness روی HMAC شمارهٔ canonical + نام کافه/شهر/شعبه و روی HMAC request key است. duplicate بی‌صدا ثبت نمی‌شود؛ پیام صریح دارد. تغییر شماره یا شعبه، درخواست مستقل است. این dedupe معنایی/fuzzy نیست. SESSION_SECRET باید پایدار بماند؛ چرخش آن dedupe و rate keyهای تازه را عوض می‌کند، بنابراین برنامهٔ rotation جدا لازم است.
- سقف hourly: global=120، IP=8، phone=3؛ bucket تراکنشی، پایدار بین worker/restart، کلید HMAC به‌جای IP/شمارهٔ خام، پاک‌سازی bucket قدیمی‌تر از 24h با فعالیت بعدی. IP فقط لایهٔ مکمل است؛ header در reverse proxy و سقف شماره/سراسری هم مهم‌اند. در خرابی DB فرم fail-closed است و تماس مستقیم می‌ماند.
- هر اکشن getSession، نقش و ممنوعیت view-as را بررسی می‌کند؛ repository نیز حساب admin/active و شمارهٔ تأییدشدهٔ واقعی را دوباره می‌خواند. revision و row lock از stale write و دو فعال‌سازی هم‌زمان جلوگیری می‌کنند.
- audit بدون شماره، IP خام یا متن یادداشت است. یادداشت داخلی فقط در inbox ادمین می‌آید. Projection مشتری فقط نام کافه، شعبه، status، تاریخ و reference است.
- تأیید human با rationale و checkbox؛ `user_place_role`، نقش global مشتری→owner، claim approved، lead active و audit در یک تراکنش هستند. خطای انتهای audit باید همه را rollback کند. فعال‌سازی از select وضعیت CRM ممنوع است.
- closed/rejected ادعای pending را رد می‌کند؛ بازگشایی pointer ادعا را پاک می‌کند تا بررسی تازه ممکن باشد؛ سابقهٔ قبلی حفظ می‌شود. CRM اجازهٔ بسته‌کردن lead فعال و لغو ضمنی مالکیت ندارد؛ لغو نقش از ابزار فعلی مدیریت کاربران شعبه و audit موجود انجام شود.

## UI و انتشار

فرم با label دائمی، autocomplete، خطای inline و alert، پیام pending، focus قابل مشاهده، RTL و کنترل 48px ساخته شده است. مقادیر فرم در خطای سرور حفظ می‌شوند. تماس و تلگرام از تنظیمات فعلی identity با fallback ارتباط موجود خوانده می‌شوند؛ اطلاعات برنامه/قیمت/SLA ساختگی نمایش داده نمی‌شود.

صفحات خصوصی inbox و پیگیری noindex هستند و به Sitemap اضافه نمی‌شوند. canonical `/for-cafes` و JSON-LD موجود حفظ شده‌اند؛ parameter منبع صفحهٔ SEO مستقل نمی‌سازد.

## معیارهای تست و کار مالک

تست واحد policy؛ integration واقعی DB جدا (race ثبت/Claim/approval، IDOR، verified-phone، stale revision، quota، privacy projection و rollback عمدی audit)؛ browser journey در 360/390/768/1440 و سه موتور؛ درخواست واقعی بدون JS در محیط جدا؛ Typecheck، CI/Build، smoke خواندنی Production.

دروازهٔ تجاری پایان فاز همچنان دو درخواست آزمایشی و یک **کافهٔ واقعی پایلوت** است. Fixture محلی جای پایلوت واقعی نیست. مالک باید پلن/قیمت، زمان پاسخ‌گویی و کافهٔ پایلوت را تعیین کند؛ هیچ مبلغ یا قول زمان پاسخ در کد فرض نشده است. تست SMS واقعی فاز صفر در این فاز بدون هماهنگی ارسال نمی‌شود.

## Rollback

از طریق PR و workflow protected شاخه production، نسخهٔ اپ قبلی بازگردد. این migration دادهٔ موجود را تغییر نمی‌دهد؛ rollback اپ باید دو جدول جدید را نگه دارد تا درخواست‌های دریافت‌شده حذف نشوند. DROP خودکار برای production ممنوع است. حذف fixture فقط روی DB `kucafe_phase1_test` یا CI با guard صریح انجام می‌شود.

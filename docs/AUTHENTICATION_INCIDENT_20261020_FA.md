# گزارش حادثهٔ احراز هویت کوکافه — ۲۰ اکتبر ۲۰۲۶

دامنهٔ تغییر فقط احراز هویت است. تنها تغییر صفحهٔ کافه، نگهداری مقصد و ادامهٔ
فرم ثبت تجربه پس از ورود است؛ نظر به‌صورت خودکار ثبت نمی‌شود.

## علت اثبات‌شدهٔ رد شدن کد پس از اشتباه

روی دیتابیس اصلی MariaDB 10.6.24، متغیر `explicit_defaults_for_timestamp=0`
و تعریف واقعی ستون چنین بود:

```sql
expires_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

ستون اولین TIMESTAMP جدول است. رفتار ضمنی نسخهٔ قدیمی MariaDB، آن را به زمان
آخرین تغییر ردیف تبدیل کرده بود. بازتولید با جدول TEMPORARY هم‌ساخت، بدون تغییر
دادهٔ اصلی: افزایش `attempts` از صفر به یک، زمان باقی‌مانده را از ۶۰ به صفر ثانیه
کاهش داد. بنابراین تلاش صحیح بعدی با همان کد، «منقضی» می‌شد. اختلاف ساعت سرور
و دیتابیس در بازخوانی نهایی ۳ میلی‌ثانیه بود؛ timezone نشست دیتابیس UTC بود.

اصلاح دو لایه دارد: همهٔ تغییرات attempts/consumed_at صریحاً expires_at را حفظ
می‌کنند؛ migration شمارهٔ 0020، ON UPDATE را حذف می‌کند و default ثابتِ گذشته
می‌گذارد تا رفتار ضمنی دوباره ایجاد نشود. زمان رکوردهای موجود تغییر نمی‌کند؛
کد منقضی یا مصرف‌شده زنده نمی‌شود. هم schema و هم اسکریپت سازگاری MariaDB و
بررسی drift به‌روز شده‌اند.

تأیید OTP اکنون در transaction و با SELECT FOR UPDATE انجام می‌شود: یک اشتباه
فقط شمارنده را افزایش می‌دهد؛ محدودیت تلاش‌ها برقرار است؛ دو تأیید هم‌زمان
حداکثر یک مصرف موفق دارند؛ درخواست با شناسهٔ قدیمی، challenge تازه را نمی‌سوزاند.
ارسال برای یک شماره، با named lock مختص همان دیتابیس و transaction سری می‌شود؛
درخواست موازی پیش از رسیدن به callback ارسال رد می‌شود و قفل پس از commit آزاد
می‌شود. در این مسیر، پرس‌وجوهای policy/repository از همان اتصال استفاده می‌کنند.

[مستند رسمی رفتار TIMESTAMP در MariaDB](https://mariadb.com/docs/server/reference/data-types/date-and-time-data-types/timestamp)

## معماری و مسیرها

| مسیر | جریان و مرجع وضعیت |
| --- | --- |
| `/auth` | AuthScreen → requestCodeAction / verifyCodeAction / passwordLoginAction → policy + userRepo → otp_code / app_user / auth_session |
| `/auth/register` | RegisterScreen → requestRegistrationCodeAction → verifyRegistrationCodeAction → اثبات امضاشدهٔ ۱۰ دقیقه‌ای → registerAction → app_user + نشست |
| `/auth/recover` | RecoverScreen → requestResetCodeAction → resetPasswordAction → OTP با purpose مستقل → تغییر رمز + ابطال نشست‌های قبلی + نشست تازه |
| `/profile/password` | کاربر دارای نشست → changePasswordAction → کنترل رمز فعلی، تغییر رمز، ابطال سایر نشست‌ها؛ حفظ مقصد در تغییر رمز اجباری |
| `/api/auth/otp` | GET فقط challenge متصل به کوکی امضاشدهٔ HttpOnly را با زمان سرور برمی‌گرداند؛ private/no-store؛ DELETE هم‌مبدأ برای تغییر شماره |
| ارسال | actions → sendVerificationCode → smsir adapter → پذیرش Provider همراه messageId → ذخیرهٔ challenge و زمان معتبر |
| تأیید | actions → اتصال شماره/purpose/id → verifyStoredOtp → transaction + قفل ردیف → مقایسهٔ hash، شمارنده یا مصرف → نشست |
| نشست | startSession → auth_session + توکن امضاشده → کوکی HttpOnly/SameSite=Lax/Secure در production → getSession/currentUser و guard صفحات/اکشن‌ها |
| بازگشت | مقصد داخلی اعتبارسنجی‌شده → تکمیل ورود → navigation مرورگر با حفظ query/hash → کافه و فرم ثبت تجربه |

محدودیت شماره، سقف ساعتی، سقف سراسری، تلاش OTP و قفل ورود رمزی حفظ می‌شوند.
حساب مسدود/غیرفعال مجاز به ورود نیست. بازیابی حساب ناموجود، پاسخ و وضعیت
challenge هم‌شکل ولی بدون ارسال پیامک دارد. مسیرهای OTP با purpose جدا می‌مانند.
مقصد خارجی، scheme-relative و backslash منتهی به origin خارجی رد می‌شود.
middleware مستقل احراز هویت در مخزن وجود ندارد؛ حفاظت حساب و دسترسی در سرور
صفحات و اکشن‌ها و resolveSessionTokens انجام می‌شود. Service Worker فقط صفحهٔ
عمومی offline و دارایی‌های آن را cache می‌کند؛ API/RSC/HTML حساب cache نمی‌شود.

## یافته‌های پنج مشکل

1. مسیر ثبت تجربه به ورود ختم می‌شد. اکنون برای کاربر جدید، ساخت حساب مقصد
   اصلی و انتخاب «قبلاً ثبت‌نام کردم؛ ورود» بالای فرم در دسترس است. query و
   hash و نیت review در تمام مراحل حفظ می‌شوند.
2. زمان ثابت به شمارندهٔ مبتنی بر `serverNow/expiresAt/resendAt` تبدیل شد.
   حرکت زمان در صفحه از `performance.now()` می‌آید؛ تغییر ساعت دستگاه TTL را
   تغییر نمی‌دهد. refresh، focus و برگشت از background از سرور بازخوانی می‌کنند.
   expiry و مجوز resend مستقل‌اند؛ هیچ ارسال خودکاری انجام نمی‌شود.
3. خطای اصلی دیتابیسِ توضیح‌داده‌شده، همراه با قفل تراکنشی و اتصال challenge
   اصلاح شده است. مصرف کد فقط با تأیید موفق یا سوختن واقعی آن انجام می‌شود.
4. WebOTP قبل از درخواست ارسال آغاز می‌شود و نتیجه به state کنترل‌شدهٔ React
   می‌رسد؛ دریافت زودهنگام با جابه‌جایی مرحله از بین نمی‌رود. درخواست قبلی با
   AbortController لغو می‌شود. autocomplete/inputmode، ورود دستی، paste و
   یکسان‌سازی ارقام فارسی و عربی برقرارند. موفقیت این callback در مرورگر QA
   جدا از اجازهٔ واقعی Android بررسی می‌شود.
5. علاوه بر خطای expires_at، فرم قبلی ثبت‌نام صرفاً طول کد را در مرحلهٔ کد
   بررسی می‌کرد و اعتبارسنجی واقعی را تا پایان مشخصات و رمز عقب می‌انداخت.
   اکنون تأیید در همان مرحله انجام می‌شود؛ ادامهٔ تکمیل حساب، با اثبات محدود
   ۱۰ دقیقه‌ای مجاز است و پذیرش OTP منقضی‌شده نیست.

در مرورگر QA، یک مشکل مستقل بازگشت نیز مشاهده شد: پس از session موفق و پاسخ
303 اکشن، fragment مقصد در پیمایش App Router از بین می‌رفت. مرحلهٔ تکمیل ورود
پیمایش کامل مرورگر را انجام می‌دهد تا صفحهٔ ناشناس cacheشده و گم‌شدن #reviews
در مسیر ورود تکرار نشود. این مسیر نیز باید در تست مرورگر تأیید شود.
این مسیر در build نهایی هم با Chromium و هم WebKit تأیید شد. در بررسی HTTP
نسخهٔ ساخته‌شده، مقایسهٔ Origin با URL داخلی Next باعث 403 هنگام «تغییر شماره»
می‌شد؛ اکنون Origin فقط با دامنهٔ عمومی تنظیم‌شده مقایسه می‌شود. درخواست
هم‌مبدأ 204 و دامنهٔ دیگر 403 می‌گیرد؛ پاک‌کردن کوکی پیش از فرم شمارهٔ جدید
تمام می‌شود تا پاسخ DELETE قدیمی کوکی تازه را پاک نکند.

## وضعیت SMS و WebOTP واقعی

فقط یک تست اصلی پیش از این بررسی انجام شده: شناسهٔ 782826321، پذیرش Provider
و تحویل با وضعیت 1 پس از ۸ ثانیه، همراه تأیید دریافت مالک. این شاهد، خرابی
همهٔ پیامک‌ها یا موفقیت همهٔ تلاش‌ها را ثابت نمی‌کند.

متن واقعی template فعلی 557141 دارای متن فارسی و کد است و خط origin-bound ندارد.
برای Chrome Android، آخرین خط باید برای دامنهٔ واقعی دقیقاً مشابه مثال ساختگی
زیر باشد (کد واقعی سایت پنج رقم است):

```text
@kucafe.ir #12345
```

طبق مستند رسمی، پیام باید بعد از شروع credentials.get برسد و دامنهٔ خط آخر با
صفحه یکی باشد. در API مستند SMS.ir، امکان ویرایش template با کلید فعلی پیدا
نشد؛ تغییر پنل Provider و آزمون گوشی واقعی هنوز نیازمند همکاری مالک است.
پیشنهاد قالب باید ابتدا با پیش‌نمایش پنل کنترل شود تا # پیش از کد واقعاً حفظ شود؛
پارامتر CODE برای تزریق newline به template استفاده نمی‌شود.

پیشنهاد برای بررسی در پنل، با فرض قالب متداول `#CODE#` در همان حساب:

```text
کد ورود به کوکافه: #CODE#

@kucafe.ir ##CODE#
```

پیش‌نمایش و سپس SMS واقعی باید نشان دهند که آخرین خط به شکل مثال پنج‌رقمی
بالا رندر می‌شود؛ هیچ متن یا footer دیگری بعد از آن نباشد.

[مستند رسمی Chrome/WebOTP](https://developer.chrome.com/docs/identity/web-apis/web-otp)،
[مستند رسمی SMS.ir](https://sms.ir/rest-api/)

## تست، انتشار و محدودیت‌ها

تست مرورگر روی 127.0.0.1:3197، با build نهایی و NODE_ENV=production و دیتابیس
جداگانهٔ kucafe_auth_qa_20261020 انجام
می‌شود. provider این محیط DEV است، کلید واقعی SMS ندارد و از اطلاعات خصوصی
production کپی نشده است. فقط یک رکورد عمومی کافه برای مسیر واقعی صفحه وارد شد.
شمارهٔ تست همان شمارهٔ مجاز مالک است. کد و token و رمز و شمارهٔ کامل در گزارش
تست یا audit چاپ نمی‌شوند. شمارهٔ مجاز از متغیر خصوصی KUCAFE_AUTH_QA_PHONE
خوانده می‌شود و در سورس منتشر نمی‌شود. لاگ DEV فقط در فایل خصوصی موقت QA
نگهداری می‌شود. استثنای کوکی بدون Secure فقط در محیط HTTP خصوصی QA فعال است؛
این تست به‌تنهایی مشاهدهٔ کوکی روی HTTPS واقعی production محسوب نمی‌شود.

- `scripts/auth-incident-browser-qa.ts`: فرم واقعی مرورگر → Server Actions →
  دیتابیس QA، signup، wrong/correct، expiry proof، ورود موجود، WebOTP mock،
  تغییر ساعت دستگاه، همگام‌سازی focus با سرور، refresh، paste واقعی، session،
  ورود با رمز، تغییر اجباری رمز، بازیابی رمز و ابطال نشست قبلی، تغییر شماره
  و بازگشت به فرم تجربه. همهٔ مراحل روی build نهایی عبور کردند.
- `scripts/auth-webkit-fallback-qa.ts`: موتور WebKit با viewport آیفون، نبود
  WebOTP، ورود کامل ارقام فارسی، اشتباه و سپس صحیح، نشست و ادامهٔ تجربه؛
  ورود با نام کاربری و رمز و حفظ hash نیز عبور کرد. کیبورد واقعی iOS تست نشده.
- `scripts/auth-http-smoke.ts`: challenge ناشناس افشا نمی‌شود، no-store، purpose
  نامعتبر، رد Origin خارجی، پذیرش Origin عمومی و رد مقصد خارجی؛ عبور کرد.
- `scripts/auth-otp-ui-smoke.ts`: فقط پاسخ‌های mock برای گذر زمان، expiry60،
  cooldown90، resend موفق، پاک‌شدن کد، cooldown طولانی‌تر و عدم ارسال خودکار.
- `otpExpiry.integration.test.ts`: فقط دیتابیس disposable؛ بازسازی schema معیوب،
  حفظ expiry در retry، مصرف یک‌باره و رقابت هم‌زمان، migration دوبار، محدودیت
  تلاش، expiry واقعی، جلوگیری از اثر challenge قدیمی روی کد جدید و جلوگیری
  از callback موازی ارسال؛ عبور کرد و در CI هم اجباری شده است.
- اجرای کامل `npm test`: تعداد ۴۸۹ موفق، صفر ناموفق، ۱۹ تست opt-in ردشده
  (skip). تست دیتابیس حیاتی بالا جداگانه با opt-in اجرا و موفق شد.
- typecheck، lint و production build موفق بودند. تست زمان/ارسال مجدد با
  پاسخ mock نیز روی build نهایی موفق بود. تاریخ گزارش نتیجهٔ انتشار نیست؛
  نسخهٔ زنده در زمان این گزارش هنوز همان 9f1e0caf1c46 است.

آزمون شبیه‌سازی موبایل/credentials، آزمون گوشی واقعی Chrome Android و تحویل
پیامک origin-bound نیست. این بخش باید پس از اصلاح template روی همان شماره و
با تعامل مالک تکمیل شود. نبود WebOTP نباید مانع ورود دستی شود.

انتشار فقط از شاخهٔ production و workflow موجود انجام می‌شود؛ checkout فعال
مالک در /opt/kucafe تغییر نمی‌کند. قبل از release، نسخهٔ image فعلی
`kucafe/app:sha-9f1e0caf1c46` و backup استاندارد deploy حفظ می‌شوند. migration
کوچک 0020 باید پیش از پذیرش تست OTP تازه اجرا و تعریف ستون بازخوانی شود.
در rollback، image قبلی قابل بازگشت است؛ اصلاح schema باقی بماند، چون برگشت
ON UPDATE همان خطا را برمی‌گرداند. رکورد OTP قدیمی نباید extend یا revive شود.

متن مأموریت ارسال‌شده در ابتدای «شرایط» بخش چهار قطع شده است؛ تا دریافت ادامهٔ
شرایط تست/انتشار، محدودهٔ قطعی مجاز همان اصلاح و QA مستقل و آماده‌سازی release است.

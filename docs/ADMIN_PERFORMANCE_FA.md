# رفع کندی پنل مدیریت — ۱۸ سپتامبر ۲۰۲۶

## علت تأییدشده

پاسخ احراز هویت‌شدهٔ داشبورد اصلی قبل از تغییر حدود ۹۵۳۳ میلی‌ثانیه بود؛ پنل کافهٔ راموز ۲۴۵ میلی‌ثانیه. گزارش `getZeroResultSearches` به‌تنهایی ۸۰۰۸ میلی‌ثانیه، آمار ترافیک ۱۰۸، سلامت داده ۱۶۲ و سایر شمارنده‌های بررسی‌شده ۳ تا ۱۰ میلی‌ثانیه زمان بردند. جدول search_log حدود ۹۴۱هزار ردیف تخمینی دارد. گزارش کل سابقه با GROUP BY و مرتب‌سازی فراوانی، در مسیر بارگذاری اولیهٔ هر تب قرار داشت. شواهد علت را در همین گزارش سرور نشان دادند، نه کش PWA.

## تغییرات

- گزارش سنگین از SSR اولیهٔ `/admin` حذف شد، نه از امکانات پنل؛ فقط در تب بازدید و جدا از سایر بخش‌ها بارگیری می‌شود.
- API مستقل با کنترل ورود، نقش واقعی مدیر سیستم، حساب فعال، رمز غیرموقت و منع حالت مشاهده به‌عنوان اضافه شد؛ پاسخ HTTP خصوصی/no-store است.
- تجمیع قبلی کل سابقه بدون تغییر Query، شمارنده، دامنهٔ زمانی یا حذف داده حفظ شد. نتیجه فقط ۶۰ ثانیه در حافظهٔ همان Backend نگهداری می‌شود؛ درخواست‌های همزمان یک محاسبه مشترک دارند و خطا کش نمی‌شود.
- Loading، خطای محدود به خود گزارش، تلاش مجدد، timeout و لغو درخواست هنگام خروج از تب اضافه شد؛ صفحه و اسکرول قفل نمی‌شوند.
- نسخهٔ worker PWA به v2 افزایش یافت تا به‌روزرسانی اختیاری آماده شود؛ سیاست کش محدود، عدم ذخیره API/قیمت/حساب و حفظ فرم‌ها تغییر نکردند.
- هنگام بررسی انتشار، اسکرپ واقعی در پس‌زمینه فعال بود و PM2 با `treekill=true` می‌توانست آن را هنگام reload متوقف کند. تنظیم `treekill:false` برای همین اپ در ecosystem ثبت شد تا reload وب‌سرور، worker مستقل اسکرپ/اعمال را نکشد؛ دستورهای توقف کامل worker باید جداگانه و صریح انجام شوند.
- در تست عمومی، اتصال keep-alive به فرآیند قدیمی سبب 404 موقت API جدید شد. فرآیند قبلی وب، پس از SIGTERM و مهلت shutdown، به‌صورت تک-PID خاتمه یافت و اسکرپ/پایتون زنده ماندند. `scripts/reload-safe.sh` برای جلوگیری از تکرار اضافه شد: CWD و PID/زمان شروع فرآیند را بررسی می‌کند، فقط وب‌سرور قبلی را پس از مهلت shutdown بازنشسته می‌کند، workerها را نمی‌کشد و آماده‌بودن Backend را می‌سنجد. فرمان deploy از این wrapper استفاده می‌کند؛ خود این انتشار Migration اجرا نکرد.
- هیچ Migration، پاک‌سازی لاگ، تغییر منو/قیمت یا بازنشانی حساب اجرا نمی‌شود.

## پذیرش و انتشار

بیلد تأییدشده: `Nbp_Nazuq6WnqKj0beaUb`.

- Build و Typecheck مستقل پس از بیلد موفق؛ `git diff --check` موفق. Lint مستقل در پروژه پیکربندی نشده است.
- پاسخ کامل احراز هویت‌شدهٔ محلی داشبورد در تست گرم ۶۶۱ میلی‌ثانیه در برابر ۹۵۳۳ قبل از تغییر؛ حدود ۹۳٪ کاهش در این نمونه. اولین پاسخ سرد بیلد جدید ۱۵۵۴ میلی‌ثانیه بود. پنل کافه در تست گرم ۳۲۸ میلی‌ثانیه بود.
- گزارش واقعی کل تاریخچه دریافت شد؛ سه درخواست همزمان بعدی در مجموع ۱۶۸ میلی‌ثانیه و با timestamp و شمارنده‌های کاملاً برابر پاسخ دادند. این کش server-side است، نه کش HTTP عمومی.
- API واقعی: بدون نشست 401؛ با نقش مالک و مشتری 403؛ با ادعای admin در توکن همان کاربر غیرمدیر همچنان 403؛ حالت مشاهده به‌عنوان 403؛ POST به API خواندنی 405.
- Chromium موبایل ۳۹۰ و دسکتاپ ۱۴۴۰: گزارش در ورود/تب عملیات درخواست نمی‌شود؛ Loading، خطای 503 شبیه‌سازی‌شده، تلاش مجدد، خروج از تب هنگام دریافت و نبود overflow/خطای Runtime تأیید شدند. خطای اولیهٔ locator متن در اسکریپت تست اصلاح شد؛ خرابی runtime برنامه نبود.
- تست نصب‌پذیری واقعی پروفایل عادی Chromium و چرخهٔ worker با دو تب موفق بود؛ حفظ فرم، به‌روزرسانی صریح، عدم کش حساب/API و عدم بازپخش درخواست آفلاین دوباره بررسی شد.

پروفایل و کوکی تست فقط در حافظه از نشست موجود و معتبر خوانده می‌شوند؛ اسکریپت تست حساب یا نشست نمی‌سازد و POSTهای مرورگر را مسدود می‌کند. تصاویر پنل خصوصی در `/opt/kucafe/var/qa/admin-performance/` با دسترسی محدود پوشه نگهداری می‌شوند و منتشر نمی‌شوند.

### نتیجهٔ عمومی نهایی

- نسخه روی اصلی و dev منتشر شد و اسکریپت `admin-performance-smoke.ts` در هر دو دامنه، نقش‌ها، نتیجهٔ واقعی/کش مشترک و UI موبایل/دسکتاپ را موفق بررسی کرد.
- پس از بازنشسته‌کردن پردازش‌های قبلی و رفع وضعیت قدیمی PM2، سه پاسخ کامل `/admin` روی HTTPS اصلی با نشست معتبر: **۶۳۹، ۲۹۴ و ۲۶۶ میلی‌ثانیه**؛ همگی HTTP 200 و دارای محتوای پنل، بدون Application error. این نمونه‌های اندازه‌گیری‌اند، نه تضمین زمان روی هر اینترنت/دستگاه.
- API بدون نشست در اصلی و dev اکنون 401 JSON است، نه 404 HTML نسخهٔ قدیمی. worker PWA و MapLibre روی HTTPS اصلی JavaScript MIME صحیح دارند.
- وضعیت قدیمی فقط برای ثبت اپ `kucafe` در PM2 بازسازی شد؛ پردازش اصلی جدید online، بدون restart loop و بدون snapshot قدیمی `_tree_pids` است و `pm2 save` اجرا شد. فایل‌های سایت/دیتابیس حذف نشدند؛ کارهای مستقل اسکرپ و پایتون، قبل و بعد زنده و دست‌نخورده ماندند.
- بازسازی فرآیند تک‌نمونه‌ای یک پنجرهٔ توقف/راه‌اندازی داشت؛ انتشار با تضمین صفر قطعی ادعا نمی‌شود. Lint مستقل یا تست آیفون/Safari فیزیکی برای این تغییر ادعا نمی‌شود.
- `reload-safe.sh`: syntax با `bash -n` و حالت `--check` در پروژهٔ production بررسی شدند. این حالت reload نمی‌کند؛ اجرای کامل wrapper به‌عنوان تست مجزا روی production انجام نشد تا ری‌استارت اضافه ایجاد نشود. مراحل عملی رفع اتصال قدیمی در همین انتشار دستی اجرا و بررسی شدند.
- سرور QA موقت 9096 خاموش شد؛ فقط main:3000 و dev:9091 در حال گوش‌دادن‌اند. هیچ Migration، واردکردن قیمت، پاک‌سازی تاریخچه، تغییر حساب یا ایجاد نشست تست انجام نشد.
- پس از بازسازی نهایی PM2، خانه، جست‌وجوی «پاستا راموز»، صفحه راموز، ورود، ثبت‌نام و نصب در هر دو دامنه HTTP 200 بودند؛ هر ۲۸ فایل CSS/JS ارجاع‌شدهٔ هر دامنه نیز HTTP 200 داشتند. وضعیت سرویس اصلی در بازبینی نهایی online و بدون restart اضافه بود.

برای انتشار بعدی، از مسیر `/var/www/kucafe` فرمان `npm run reload:safe` را پس از بیلد تأییدشده اجرا کن؛ `bash scripts/reload-safe.sh --check` فقط CWD/PID را بررسی می‌کند. اجرا از نسخهٔ `/opt/kucafe` وقتی PM2 روی production است، پیش از reload رد می‌شود تا مسیر اصلی ناخواسته عوض نشود. فرمان عمومی `npm run deploy` مانند قبل شامل Migration است؛ این انتشار فقط source/بیلد تأییدشده را منتقل کرد و آن فرمان را اجرا نکرد.

## محدودیت واقعی

اولین دریافت گزارش کامل پس از راه‌اندازی یا انقضای کش هنوز تجمیع کل تاریخچه را انجام می‌دهد و ممکن است چند ثانیه زمان ببرد؛ دیگر مانع ورود یا کار با پنل نیست. زیر بار فعلی، MariaDB مصرف CPU بالا دارد و Queryهای جست‌وجوی ترکیبی آیتم نیز در حال اجرا دیده شدند؛ رفع این مسیر مستقل بدون بررسی دقیق ادعا نمی‌شود. اگر تاریخچه باز هم رشد کند، pre-aggregation یا گزارش تجمیعی دوره‌ای مرحلهٔ بعد است؛ کاهش پنهانی سابقه/اعداد انجام نشده است.

# نیازسنجی انتشار روی سرور لینوکسی — دامنهٔ `kucafe.ir`

این سند **بررسی** است، نه پیاده‌سازی. پنج سؤال پرسیده شده و هر پنج جواب از
خواندن خودِ مخزن آمده، نه از حدس. جایی که چیزی **نیست**، صریح نوشته شده.

---

## خلاصهٔ یک‌نگاه

| سؤال | جواب کوتاه |
| --- | --- |
| روی سرور چه نصب شود؟ | Node 24 LTS · MySQL 8.4 (با سه تنظیم اجباری) · Nginx + TLS · systemd |
| مهاجرت داده؟ | سه بستهٔ جدا: دیتابیس (۱۹MB با mysqldump) · تصاویر (۹۹۰MB با rsync) · کد (git) |
| بکاپ؟ | **هیچ‌چیز نیست.** نه اسکریپت، نه در پنل. طرح پیشنهادی در بخش ۳ |
| تغییرات سمت سایت؟ | ۴ مورد اجباری + یک شکاف واقعی: **۱۹ جای هاردکدشدهٔ «کافه‌گرد»** |
| تغییر لوگو از پنل؟ | **نه.** ولی نصف زیرساختش هست؛ تسک کوچکی است |

## ۱. چه چیزی روی سرور مقصد نصب شود

### توزیع

**Ubuntu 24.04 LTS** یا **Debian 12**. عمداً Alpine نه: `sharp` روی musl به
باینری جدا و کتابخانه‌های سیستمی نیاز دارد، و بدون دلیل دردسر می‌سازد.

### Node.js

| | |
| --- | --- |
| نیاز حداقلی Next 15.5 | ۱۸٫۱۸ |
| نسخهٔ محلی این پروژه | v24.18.1 |
| **پیشنهاد** | **Node 24 LTS** (همان محلی) — یا ۲۲ LTS اگر محافظه‌کارانه‌تر می‌خواهید |

نصب از `nodesource` یا `nvm`. `npm` همراهش می‌آید.

### MySQL — سه تنظیم که **اجباری** است

MySQL **8.4 LTS** (همان نسخهٔ محلی: `8.4.11`). در `/etc/mysql/my.cnf`:

```ini
[mysqld]
character-set-server   = utf8mb4
collation-server       = utf8mb4_unicode_ci
default-time-zone      = '+00:00'
```

هر سه از تجربهٔ واقعی همین پروژه آمده‌اند:

- **`utf8mb4`** — بدون آن، ایموجی در نام آیتم‌ها («وسترن🌶️») و بعضی
  نیم‌فاصله‌ها می‌شکنند. داده واقعاً ایموجی دارد.
- **`default-time-zone='+00:00'`** — این یکی **تلهٔ گران** است. سرور محلی روی
  `+03:30` بود ولی درایور تایم‌استمپ‌ها را UTC می‌خواند؛ نتیجه این بود که هر
  `DEFAULT CURRENT_TIMESTAMP` سه‌ساعت‌ونیم در آینده نوشته می‌شد و یک قفل
  ۱۵‌دقیقه‌ای، ۱۳٬۵۰۰ ثانیه خوانده می‌شد. **این تنظیم باید قبل از ایمپورت داده
  اعمال شود**، وگرنه همان جابه‌جایی روی داده‌ی منتقل‌شده تکرار می‌شود.
- `collation` — برای یکسان‌بودن مرتب‌سازی فارسی با محلی.

بعد از نصب: یک کاربر و دیتابیس با `utf8mb4`:

```sql
CREATE DATABASE kucafe CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kucafe'@'localhost' IDENTIFIED BY '<رمز قوی>';
GRANT ALL PRIVILEGES ON kucafe.* TO 'kucafe'@'localhost';
```

**یک نکتهٔ اختیاری:** `innodb_ft_min_token_size` پیش‌فرض ۳ است، یعنی واژه‌های
دوحرفی در جست‌وجوی FULLTEXT ایندکس نمی‌شوند. برای فارسی معمولاً مشکلی نیست
(«چای» سه‌حرفی است) ولی اگر خواستید ۲ بگذارید، **باید ایندکس‌های FULLTEXT را
از نو بسازید** — بعد از ایمپورت این کار سخت‌تر است، پس اگر می‌خواهید، همین اول
تصمیم بگیرید.

### Nginx + HTTPS — **اجباری، نه اختیاری**

کوکی نشست در تولید `secure` است:

```ts
secure: process.env.NODE_ENV === 'production'
```

یعنی **بدون HTTPS هیچ‌کس نمی‌تواند وارد شود** — مرورگر کوکی را نمی‌فرستد و
ورود بی‌صدا کار نمی‌کند. پس `certbot` و گواهی Let's Encrypt جزء نصب اولیه است،
نه کار بعدی.

Nginx دو کار مهم دیگر هم می‌کند:

1. **سرو مستقیم فایل‌های ثابت.** ۱۴٬۴۸۰ تصویر و ۱۵ فونت نباید از Node رد شوند.
   `location /media/` و `location /_next/static/` را مستقیم از دیسک بدهید —
   بزرگ‌ترین برد سرعتی این استقرار همین است.
2. `proxy_set_header X-Forwarded-Proto https` تا Next بداند پشت TLS است.

`client_max_body_size` را هم از حالا روی چیزی مثل `10m` بگذارید — برای وقتی
آپلود تصویر اضافه شد (بخش ۵).

### مدیریت فرآیند

`systemd` (توصیه) یا `pm2`. سرویس `next start` را روی `127.0.0.1:3000` بالا
بیاورد و Nginx به آن پروکسی کند. `Restart=always` و `EnvironmentFile` برای
`.env.local`.

### حافظه برای build

روی این ماشین (۴GB، با MySQL روشن) build با segfault می‌ترکید و
`next.config.mjs` عمداً تک‌فرآیندی شده:

```js
experimental: { workerThreads: false, cpus: 1 }
```

روی سروری با **۴GB یا بیشتر آزاد** می‌توانید این دو خط را بردارید تا build
چند برابر سریع‌تر شود. اگر سرور کوچک است، همان‌طور بمانند.

**یک درس عملیاتی از همین امروز:** `npm run build` را روی سروری که در حال
اجراست نزنید. `.next` نیم‌بند شد و همهٔ صفحه‌ها ۵۰۰ دادند
(`Cannot find module './vendor-chunks/mysql2.js'`). ترتیب درست: سرویس را
بخوابانید → build → بالا بیاورید. یا `output: 'standalone'` را فعال کنید و
دیپلوی را اتمیک کنید (بخش ۴).

### آنچه لازم **نیست**

| | چرا |
| --- | --- |
| ابزار رندر نقشه (mapnik / tilemaker) | تایل‌ها در لحظه با `geojson-vt` ساخته می‌شوند، کاملاً جاوااسکریپت |
| فایل PBF ایران (۲۲۸MB) | فقط برای **استخراج دوباره** لازم است؛ خروجی‌اش (۱۸MB GeoJSON) در git است |
| کتابخانهٔ سیستمی برای `sharp` | روی لینوکس x64/glibc باینری آماده نصب می‌شود |
| Redis / صف / CDN | هیچ‌کدام استفاده نمی‌شوند |

## ۲. مهاجرت داده — سه بستهٔ جدا

مهم است که این‌ها را جدا ببینید، چون روشِ هرکدام متفاوت است و **دو تای‌شان در
git نیستند**.

| بسته | حجم | در git؟ | روش |
| --- | --- | --- | --- |
| دیتابیس | **۱۹٫۲MB** · ۳۷ جدول | ❌ | `mysqldump` |
| تصاویر (`public/media/`) | **۹۹۰MB** · ۱۴٬۴۸۰ فایل | ❌ (gitignore) | `rsync` |
| کد + نقشه + فونت | ~۲۰MB | ✅ | `git clone` |
| `.env.local` | چند خط | ❌ | دستی |

### ۲.۱ دیتابیس

روی مبدأ:

```bash
mysqldump --default-character-set=utf8mb4 \
          --single-transaction --routines --triggers \
          --hex-blob cafegard > kucafe-$(date +%F).sql
```

روی مقصد — **بعد از** اعمال `default-time-zone='+00:00'` و restart:

```bash
mysql --default-character-set=utf8mb4 kucafe < kucafe-2026-08-06.sql
npm run db:verify     # ایندکس‌های FULLTEXT و سلامت داده را بررسی می‌کند
```

**چرا `db:verify` مهم است:** `drizzle-kit push` یک بار سه ایندکس FULLTEXT را
بی‌صدا انداخت و جست‌وجو فقط وقتی می‌شکست که کسی جست‌وجو می‌کرد. آن اسکریپت
دقیقاً برای همین ساخته شد. حتماً بعد از ایمپورت اجرایش کنید.

**راه جایگزین (توصیه نمی‌شود):** شمای خالی با `npm run db:push` بسازید و بعد
`npm run import:cafes`. این کار داده را از فایل منبع بازمی‌سازد ولی **کاربران،
نظرها، آمار بازدید و تنظیمات را نمی‌آورد**. برای مهاجرت، `mysqldump` جواب است.

### ۲.۲ تصاویر

```bash
rsync -avz --progress public/media/ user@server:/srv/kucafe/public/media/
```

اندازهٔ واقعیِ روی دیسک (اندازه‌گیری‌شده، نه تخمین):

| پوشه | حجم | چیست |
| --- | --- | --- |
| `media/item/` | ۸۰۶MB | تصویر آیتم‌های منو — بخش اصلی |
| `media/section/` | ۱۷۲MB | تصویر دسته‌های منو |
| `media/logo/` | ۱۱MB | لوگوی مجموعه‌ها |
| **کل `public/`** | **۹۹۰MB** | با فونت‌ها و تصاویر ثابت |

*(جدول `media` در دیتابیس `SUM(bytes) = 1,062MB` می‌دهد؛ آن عدد بایتِ **منبع**
را ثبت کرده و روی دیسک نسخهٔ WebP نشسته، پس دو عدد یکی نیستند. برای برنامه‌ریزی
rsync و بکاپ، همان ۹۹۰MB معتبر است.)*

یک گیگابایت با ۱۴هزار فایل کوچک؛ `rsync` بهتر از `scp` است چون قابل ادامه‌دادن
است و در اجرای دوم فقط تفاوت‌ها را می‌فرستد.

**چرا دوباره دانلود نکنیم؟** `npm run media:download` هست، ولی **۷۸ لینک منبع
از قبل مرده‌اند** و این عدد فقط بیشتر می‌شود. تصاویری که یک بار گرفته شده‌اند،
سرمایه‌اند. `rsync` کنید.

### ۲.۳ کد

```bash
git clone <repo> /srv/kucafe && cd /srv/kucafe
npm ci
# .env.local را بسازید (بخش ۴)
npm run build
```

GeoJSONهای نقشه (۱۸MB) داخل git هستند، پس نقشه بی‌هیچ کار اضافه‌ای کار می‌کند.

### ۲.۴ `.env.local`

دستی ساخته می‌شود. **`SESSION_SECRET` تازه بسازید** (`openssl rand -hex 32`) —
نه همان محلی. عوض‌کردنش نشست‌های موجود را باطل می‌کند که در استقرار تازه
اهمیتی ندارد.

### ۲.۵ سه چیز که بعد از مهاجرت باید بررسی شود

```bash
npm run db:verify        # ساختار، ایندکس، شمار داده
npm run db:smoke         # فارسی، ایموجی، دقت مختصات، FULLTEXT
npm run pages:smoke      # ۲۱ صفحهٔ واقعی، با نشست
```

اگر ایموجی یا نیم‌فاصله شکسته باشد، `db:smoke` می‌گیردش — و علتش تقریباً همیشه
`utf8mb4` است که جایی از زنجیره (دیتابیس، جدول، اتصال، فایل dump) جا افتاده.

## ۳. بکاپ — وضعیت واقعی و طرح پیشنهادی

### وضعیت امروز: هیچ‌چیز

بررسی شد و صریح می‌گویم:

- ❌ اسکریپت بکاپ وجود ندارد (`scripts/` را کامل خواندم)
- ❌ در پنل ادمین هیچ امکان بکاپی ساخته نشده — تب **عملیات** پنج کار دارد
  (رول‌آپ آمار، پاک‌سازی بازدید، بازمحاسبهٔ مشتق، بازمحاسبهٔ امتیاز، خالی‌کردن
  کش) و **هیچ‌کدام بکاپ نیست**
- ❌ `docs/ACCESS.md` بخش ۹ خودش می‌گوید «بکاپ خودکار: ندارد» — و آن سند از
  دوران فایل‌های JSON است و **بیات** است (بخش ۶ همین سند)

`audit_log` رد پای تغییرات را دارد، ولی **بکاپ نیست**: با آن نمی‌شود داده را
برگرداند.

### چه چیزی باید بکاپ شود

| چه چیزی | حجم | هرچند وقت | چرا |
| --- | --- | --- | --- |
| دیتابیس | ۱۹MB | **روزانه** | کاربران، نظرها، آمار، تنظیمات — تنها نسخه‌اش همین است |
| `public/media/` | ۹۹۰MB | هفتگی یا افزایشی | فقط با افزودن کافه/تصویر تازه رشد می‌کند |
| `.env.local` | چند خط | یک‌بار، آفلاین | بازسازی‌شدنی نیست (`SESSION_SECRET`) |

و آنچه **لازم نیست**: `.next` و `node_modules` (بازساختنی)، `src/data/map`
(در git است)، `all-cafe-data/` (آرشیو منبع — یک نسخه آفلاین کافی است).

### طرح پیشنهادی — و چرا این شکل

**بکاپ را cron بگیرد، پنل فقط نگاه کند.**

اجرای `mysqldump` از داخل یک درخواست وب سه مشکل دارد: چند ده ثانیه طول می‌کشد
و timeout می‌خورد، به دسترسی shell از فرآیند وب نیاز دارد، و اگر دو نفر با هم
بزنند دو dump هم‌زمان می‌سازد. پس:

```
۱. scripts/backup.ts        → dump + tar از media، با نگه‌داری N نسخهٔ آخر
۲. cron روزانه              → همان اسکریپت، ساعت کم‌ترافیک
۳. تب «بکاپ» در پنل ادمین   → آخرین بکاپ کِی بود، چند مگابایت، سالم است؟
                              + دکمهٔ دانلود آخرین نسخه
                              + (اختیاری) «بکاپ فوری» که اسکریپت را در پس‌زمینه صدا می‌زند
```

پنل به این شکل **ناظر** است نه مجری — و مهم‌تر: اگر بکاپ سه روز نگرفته، ادمین
**می‌بیند**. بکاپی که هیچ‌کس وضعیتش را نمی‌بیند، تا روزِ بازگردانی معلوم
نمی‌شود که خراب بوده.

دو تنظیم هم برایش لازم می‌شود که به رجیستری اضافه شوند: «چند نسخه نگه داشته
شود» و «مسیر بکاپ».

**و یک بند که معمولاً فراموش می‌شود:** بکاپِ آزمایش‌نشده بکاپ نیست. اسکریپت
باید یک حالت «بازگردانی روی دیتابیس موقت + `db:verify`» داشته باشد تا هر ماه
یک بار ثابت شود قابل برگشت است.

## ۴. تغییرات سمت سایت برای `kucafe.ir`

### ۴.۱ اجباری — چهار مورد

**`.env.local` روی سرور:**

```ini
NEXT_PUBLIC_SITE_URL=https://kucafe.ir
DATABASE_URL=mysql://kucafe:<pass>@127.0.0.1:3306/kucafe
SESSION_SECRET=<openssl rand -hex 32>
AUTH_DEV_MODE=false
SMSIR_API_KEY=...
SMSIR_TEMPLATE_ID=...
ADMIN_PHONES=09306819085
```

`NEXT_PUBLIC_SITE_URL` **در زمان build** خوانده می‌شود (چون `NEXT_PUBLIC_` است)
— پس باید **قبل از** `npm run build` سر جایش باشد، نه بعدش.

بررسی شد که این متغیر واقعاً همه‌جا جاری می‌شود: `metadataBase`،
`alternates.canonical`، `sitemap.xml`، `robots.txt` و `@id` در JSON-LD — همه از
`absoluteUrl()` می‌آیند که از `SITE_URL` می‌خواند. یک نقطه، همه‌جا.

**AUTH_DEV_MODE و تنظیم پنل:** بعد از استقرار، از تب تنظیمات → گروه «ورود و
امنیت» → «حالت توسعهٔ پیامک» را هم **خاموش** کنید. آن تنظیم بر env مقدم است،
پس اگر روشن بماند پیامکی ارسال نمی‌شود حتی با کلید درست.

### ۴.۲ یک تلهٔ خاموش که باید بسته شود

`src/routes.ts` خط ۴۶:

```ts
export const SITE_URL = process.env.NEXT_PUBLIC_SITE_URL ?? 'https://cafegard.ir'
```

اگر متغیر محیطی جا بیفتد، سایت **بی‌هیچ خطایی** بالا می‌آید و همهٔ
`canonical`ها، `sitemap` و JSON-LD به `cafegard.ir` اشاره می‌کنند — یعنی به
گوگل می‌گوییم «محتوای اصلی جای دیگری است». این بدترین نوع خرابی است: هیچ لاگی
ندارد و چند هفته بعد در رتبه دیده می‌شود.

**پیشنهاد:** یا پیش‌فرض به `kucafe.ir` عوض شود، یا (بهتر) نبودنش به
`checkConfig()` اضافه شود تا در بالای پنل ادمین هشدار قرمز بدهد — همان‌جایی که
`SESSION_SECRET` نبودن الان هشدار می‌دهد.

### ۴.۳ شکاف واقعی: **۱۹ جای هاردکدشدهٔ «کافه‌گرد»**

نام سایت در تسک ۱۴ تنظیم شد و در متادیتا، بنر و پیامک از تنظیمات می‌آید. ولی
**۱۹ جا** هنوز رشتهٔ ثابت دارند. اگر برند «کوکافه» شود، این‌ها «کافه‌گرد»
می‌مانند:

| جا | چه چیزی |
| --- | --- |
| `components/layout/SiteHeader.tsx` | نام برند کنار لوگو + `alt` تصویر |
| `components/layout/SiteFooter.tsx` | نام برند، شعار، **متن کپی‌رایت** |
| `components/auth/AuthScreen.tsx` | نام کنار لوگو در صفحهٔ ورود |
| ۸ صفحه (`profile/*`، `admin/venue`، `search`) | `title` متادیتا: «... — کافه‌گرد» |
| `cafe/[slug]` و `mashhad/[district]` | اولین حلقهٔ breadcrumb در JSON-LD |
| `profile/actions.ts` و ۲ کامپوننت | «کاربر کافه‌گرد» به‌عنوان نام پیش‌فرض نویسندهٔ نظر |
| `core/map/style.ts` | نام استایل نقشه |

از این‌ها **breadcrumb در JSON-LD** و **کپی‌رایت فوتر** بیشترین اهمیت را دارند:
اولی را گوگل می‌خواند، دومی را هر بازدیدکننده می‌بیند.

خوبی‌اش این است که راه‌حل ساده است: هرکدام یک `settings.siteName` می‌خواهد.
برای صفحه‌های سرور مستقیم؛ برای هدر و فوتر (کامپوننت کلاینت) به‌صورت prop از
layout. تسک کوچکی است ولی **قبل از انتشار** باید انجام شود، نه بعدش.

### ۴.۴ پیشنهاد فنی: `output: 'standalone'`

الان تنظیم نشده، یعنی سرور به کل `node_modules` نیاز دارد و دیپلوی
اتمیک نیست (همان مشکل `.next` نیم‌بند). با `standalone`:

- خروجی یک پوشهٔ خودکفا می‌شود
- می‌شود در جای تازه ساخت و با یک `symlink` سوئیچ کرد → دیپلوی بی‌قطعی
- حجم `node_modules` روی سرور لازم نیست

تغییر کوچکی است ولی روی سرور تولیدی ارزشش را دارد.

### ۴.۵ چیزهایی که **نیازی به تغییر ندارند**

- مسیر `/mashhad/[district]` — با برند تازه هم درست است و برای SEO محلی خوب
- `robots.txt` و `sitemap.xml` — خودشان از دامنهٔ تازه تبعیت می‌کنند
- نقشه — کاملاً آفلاین است، هیچ درخواست بیرونی ندارد (در `pages:smoke` بررسی
  می‌شود که استایلش هیچ `https://` نداشته باشد)
- تصاویر — همه لوکال، هیچ CDN بیرونی (این هم بررسی خودکار دارد)

## ۵. تغییر لوگو از پنل ادمین

### جواب: نه، الان امکانش نیست

لوگو یک **فایل ثابت** است و مسیرش در کد ثابت:

```ts
// src/components/layout/SiteHeader.tsx
const LOGO_SRC = '/logo-sm.webp'
```

فایل‌های مرتبط: `public/logo-sm.webp` (۶KB — همان که در هدر و صفحهٔ ورود
دیده می‌شود)، `public/logo.png` (۹۹۳KB)، `public/favicon.svg`،
`public/cafe-photo.webp` (۲۱۶KB، تصویر پیش‌فرض).

### چه چیزی برای انجامش لازم است — و چه بخشی از قبل هست

خبر خوب: **بیشتر زیرساختش ساخته شده**، چون خط لولهٔ تصویر برای ۱۴هزار عکس منو
از قبل وجود دارد:

| قطعه | وضعیت |
| --- | --- |
| تبدیل به WebP در دو اندازه | ✅ `core/media/derive.ts` → `deriveImage()` با `sharp` |
| مسیرسازی و ذخیره روی دیسک | ✅ `core/media/store.ts` → `mediaRelativePath()` |
| نوع رسانهٔ `'upload'` در جدول | ✅ در `MediaKind` از قبل تعریف شده |
| تنظیم `siteLogoPath` | ❌ باید به رجیستری اضافه شود |
| اکشن آپلود در پنل | ❌ نیست |
| خواندنش در هدر/فوتر/ورود | ❌ الان ثابت است |

یعنی کار واقعی: یک تنظیم + یک server action آپلود + پاس‌دادن مسیر به سه
کامپوننت. **تسک کوچکی است** و در همان قدم می‌شود favicon و تصویر پیش‌فرض
اشتراک‌گذاری (OG image) را هم قابل تغییر کرد.

**یک نکتهٔ عملیاتی:** فایل آپلودشده در `public/` می‌نشیند که در `.gitignore`
است. پس بعد از افزودن این قابلیت، لوگو هم جزء **بکاپ تصاویر** می‌شود — یک دلیل
دیگر که بکاپ (بخش ۳) باید قبل از این قابلیت آماده باشد.

## ۶. یک یافتهٔ جانبی: `docs/ACCESS.md` بیات است

در جریان این بررسی معلوم شد سند دسترسی‌ها از **دوران قبل از MySQL** است و
اگر کسی در استقرار به آن تکیه کند، گمراه می‌شود. مثال‌ها:

| سند می‌گوید | واقعیت امروز |
| --- | --- |
| «`src/data/users.json` — کاربران و نقش‌ها» | کاربران در MySQL، جدول `app_user` |
| «`places.generated.json` — ۱۰۰ کافه» | ۳۳۱ کافه در MySQL |
| «نقشه: grid با پین، نه تایل واقعی» | نقشهٔ برداری آفلاین با ۷۹٬۵۹۷ عارضه |
| «ویرایش منو در پنل مالک: ذخیره نمی‌شود» | ذخیره می‌شود، با رد پا در `audit_log` |
| «ثبت نظر واقعی نیست» | واقعی است، با صف تأیید |
| «بکاپ سه فایل اول را بگیر» | آن فایل‌ها دیگر منبع حقیقت نیستند |

و مرتبط با همین: **`src/data/userStore.ts` کد مرده است** — هیچ‌جا import
نمی‌شود (فقط در یک کامنت در `userRepo.ts` به‌عنوان «جایگزینش» نام برده شده)
ولی هنوز در git است و `users.json` و `otp.json` کنارش روی دیسک مانده‌اند با
هش رمزهای قدیمی. این‌ها gitignore هستند، پس به سرور نمی‌روند؛ ولی پاک‌کردنشان
قبل از استقرار، هم بهداشتِ کد است هم یک منبع سرگردانِ داده کمتر.

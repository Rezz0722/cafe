## ۳. شیفت شکسته ذخیره شد

```
name                   dow  shift_index  opens_at  closes_at  crosses_midnight
جان بوتیک رستوران      0    1            20:00:00  23:30:00   0
جان بوتیک رستوران      2    1            12:00:00  23:30:00   0
```

`shift_index = 1` یعنی شیفت دوم همان روز — چیزی که شمای Postgres قبلی
نمی‌توانست ذخیره کند. ۲٬۴۲۹ شیفت وارد شد.

## ۴. هشدارهای ساعت از ۵۵۸ به ۱۰ رسید

تحلیل تسک ۰۱ گفته بود ۵۵۸ «بازه‌ی غیراستاندارد» وجود دارد. بعد از اینکه
پارسر شیفت شکسته، ساعت بی‌دقیقه (`8-24`) و ساعت ۲۴+ را فهمید، فقط **۱۰**
مورد باقی ماند — همان تایپ‌های واقعاً خراب مثل `93:0-22`.

این ۱۰ مورد **حدس زده نشدند**. یک ساعتِ اشتباه از یک ساعتِ خالی بدتر است،
چون کاربر با اعتماد به آن راه می‌افتد و به در بسته می‌رسد.

## ۵. تشخیص غیرکافه‌ها کار کرد

۵ مجموعه با `kind = 'shop'` و وضعیت `draft` وارد شدند، یعنی در سایت عمومی
دیده نمی‌شوند ولی داده‌شان هست:

- `گرینو` — کاکتوس‌فروشی (قیمت‌ها تا ۱۰ میلیون)
- `تاپ منو مارکت` — عطر و پوشاک (تا ۱۱۳ میلیون)
- `تخم مرغ آمین` — عمده‌فروشی تخم‌مرغ
- `آرایشی گلریز` · `رز بیوتی` — خدمات آرایشی

بدون این تشخیص، «ارزان‌ترین کافه‌های مشهد» یک عطر ۱۱۳ میلیونی نشان می‌داد و
میانه‌ی قیمت کل شهر خراب می‌شد.

## ۷. باگی که در لایه‌ی پرس‌وجو پیدا و رفع شد

`listDistricts` برای همه‌ی محله‌ها «۰ کافه» برمی‌گرداند، در حالی که همان SQL
دستی درست جواب می‌داد. علت:

```ts
// غلط — drizzle نام جدول را حذف می‌کند
sql`(SELECT COUNT(*) FROM place WHERE place.district_id = ${districtTable.id})`
// تولید می‌کند:
// (SELECT COUNT(*) FROM place WHERE place.district_id = `id`)
```

MySQL آن `` `id` `` بی‌نام را به جدولِ **درونی** (`place`) نسبت می‌دهد، پس
شرط به `place.district_id = place.id` تبدیل می‌شود که همیشه false است —
**بدون هیچ خطایی**.

رفع: در زیرپرس‌وجوی همبسته، ارجاع به ستون بیرونی صریح و با نام جدول نوشته
می‌شود (`district.id`). همین اصلاح روی فیلتر facet و dish هم اعمال شد؛
آن دو تصادفاً کار می‌کردند (چون `place_facet` ستون `id` ندارد) ولی به همان
اندازه شکننده بودند.

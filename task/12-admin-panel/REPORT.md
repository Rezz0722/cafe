# تسک ۱۲ — پنل مدیریت ✅

## چه چیزی ساخته شد

شش تب، همه روی داده‌ی واقعی:

| تب | محتوا |
| --- | --- |
| **صف کار** | نظرهای در انتظار تأیید + کافه‌های ثبت‌شده توسط کاربران |
| **بازدید** | آمار ۳۰ روزه، نمودار روزانه، پرترددترین صفحه‌ها، دستگاه، مرجع، **جست‌وجوهای بی‌نتیجه** |
| **مجموعه‌ها** | ۳۳۱ مکان با تغییر وضعیت انتشار + لینک ویرایش |
| **کاربران** | جست‌وجو، نقش، مسدودی، انتساب کافه، **ورود به پنل او** |
| **اعتبارنامه** | ساخت حساب کافه (یک قدم) + بازنشانی رمز هر حساب |
| **سلامت داده** | ۱۴ سنجه + ناقص‌ترین پروفایل‌ها + تصویرهای ناموفق + تنظیمات |

تب اول **صف کار** است نه آمار: ادمین معمولاً آمده کاری انجام بدهد، نه نمودار
ببیند. نشانِ عددی روی تب، کارهای منتظر را نشان می‌دهد.

## آمار بازدید — از صفر ساخته شد

قبل از این تسک هیچ داده‌ی بازدیدی وجود نداشت. سه تکه اضافه شد:

1. `PageViewTracker` — کلاینت، روی تغییر مسیر. با **`sendBeacon`** نه
   `fetch`: بازدیدِ کسی که سریع صفحه را می‌بندد گم نمی‌شود، و آن‌ها دقیقاً
   کسانی هستند که باید بدانیم چرا رفتند.
2. `POST /api/track` — کوکیِ بازدیدکننده را می‌سازد (در App Router نمی‌شود از
   داخل رندر کوکی نوشت) و ردیف می‌زند.
3. `core/analytics/` — ثبت و گزارش.

### چرا خودمان و نه گوگل آنالیتیکس

گوگل آنالیتیکس در ایران بدون فیلترشکن بار نمی‌شود، پس آمارش ناقص است. به‌علاوه
داده‌ی بازدیدِ هر کافه باید **داخل پنل کافه‌دار** دیده شود، و «کدام کافه بیشتر
دیده شد» سیگنالی است که در رتبه‌بندی هم به کار می‌آید.

### تصمیم‌های آماری

- **IP ذخیره نمی‌شود.** شمارش یکتا با یک کوکیِ بی‌نامِ تصادفی است. برای آمار
  یک راهنمای کافه کافی است و ذخیره‌ی IP فقط بدهیِ حقوقی می‌آورد.
- **ربات‌ها جدا شمرده می‌شوند، نه حذف.** اگر حذف شوند، معلوم نمی‌شود چرا
  ترافیک سرور با آمار نمی‌خواند؛ اگر با آدم‌ها قاطی شوند، آمار بی‌معنی است.
  ربات `view_count` کافه را بالا نمی‌برد — آن عدد را کافه‌دار می‌بیند.
- **مسیر بدون query ذخیره می‌شود.** با query، هر ترکیب فیلتر یک «صفحه»ی جدا
  می‌شد و گزارش پرترددترین صفحات بی‌معنی می‌شد.
- **شکستِ ثبت آمار هرگز به کاربر نمی‌رسد** — آمار مهم است، ولی نه به قیمتِ
  خرابی صفحه.
- نمودار روزانه با **CSS خالص** است، بدون کتابخانه: یک نمودار میله‌ای ارزش
  ۵۰ کیلوبایت جاوااسکریپت را ندارد.

### باارزش‌ترین گزارش: جست‌وجوهای بی‌نتیجه

`search_log` با `result_count = 0` مستقیماً می‌گوید کاربر چه چیزی خواسته که
نداریم. هر ردیف یا یک کافه‌ی جامانده است یا یک facet که واژگانش کم دارد.

## اعتبارنامه — خواسته‌ی صریح پروژه

### ساخت حساب کافه در **یک قدم**

کارِ واقعیِ ادمین این است: «برای کافه‌ی شایر حسابی بساز که بتواند منویش را
ویرایش کند». یک فرم، سه کار: ساخت کاربر + صدور رمز + انتساب مجموعه.

اگر سه صفحه‌ی جدا بود، هر بار یکی فراموش می‌شد و کافه‌داری می‌ماند که وارد
می‌شود ولی پنلش خالی است.

- **یوزرنیم بدون شماره کافی است** — ادمین مجبور نیست برای هر کافه یک شماره‌ی
  جعلی بسازد.
- اگر شماره از قبل حساب دارد، **همان حساب** مالک می‌شود. حساب دوم با یک
  شماره، کاربر را از سابقه‌اش جدا می‌کند.
- رمز خالی = تولید خودکار ۱۴ کاراکتری.

### رمز فقط **یک‌بار** دیده می‌شود

فقط هشِ رمز ذخیره می‌شود، پس بعد از بستن آن پیام هیچ‌کس — از جمله ادمین —
نمی‌تواند ببیندش. این عمدی است: رمزی که در دیتابیس قابل خواندن باشد، با یک
نفوذ همه‌ی حساب‌ها را می‌دهد. اگر گم شد، رمز تازه صادر می‌شود.

هر رمزِ ادمین‌ساخته `mustChangePassword` می‌گیرد، چون از کانالی مثل واتساپ
می‌رسد و آن کانال امن نیست.

### رمز دائمی برای کاربران عادی هم

همان فرم برای هر حسابی کار می‌کند. کاربری که با کد پیامکی ساخته شده، رمز
دائمی می‌گیرد و تا وقتی پیامک در دسترس نیست، این تنها راه ورودش است.

## ورود مستقیم به همه‌ی پنل‌ها

دکمه‌ی «ورود به پنل او» کنار هر کاربر. مالک به پنل کافه می‌رود و کاربر عادی
به پنل خودش — همان جایی که خودش بعد از ورود می‌دید.

محدودیت‌ها (در `core/auth/impersonation.ts`):
- **کوکی دوم** — نشست ادمین دست‌نخورده می‌ماند، پس راه برگشت نمی‌سوزد
- **نیم‌ساعت اعتبار** — پنجره‌ی یک کار پشتیبانی، نه نشست دوم
- **فقط‌خواندنی** — همه‌ی اکشن‌های نوشتن با دیدن `actor` رد می‌شوند
- **ادمین دیگر قابل مشاهده نیست** — وگرنه می‌شد کار مدیریتی را زیر نام او کرد
- نوار همیشه‌دیده در بالای سایت + ثبت در `impersonation_log`

## قواعد امنیتی

| قاعده | چرا |
| --- | --- |
| هر اکشن با `requireAdminActor` شروع می‌شود | بررسی نقش در صفحه کافی نیست؛ اکشن‌ها endpoint واقعی‌اند |
| در حالت «مشاهده» هیچ نوشتنی مجاز نیست | حتی برای ادمین |
| هر تغییر در `audit_log` با `before`/`after` | ادمین قوی‌ترین نقش است؛ بدون رد پا اشتباهش پیدا نمی‌شود |
| ادمین نقش/مسدودیِ **خودش** را عوض نمی‌کند | وگرنه از پنل بیرون می‌افتد و راهی جز اسکریپت CLI نمی‌ماند |
| هشِ رمز هرگز به کلاینت نمی‌رود | فقط «رمز دارد یا نه» |

## تأیید نظر ← امتیاز مکان

`rating_sum`/`rating_count` روی ردیف مکان کش می‌شوند و **هر تغییر وضعیت نظر**
(چه تأیید و چه رد) بازمحاسبه‌شان می‌کند. تست هر سه حالت را می‌بندد:

```
✓ نظر تأییدنشده امتیاز را عوض نمی‌کند
✓ تأیید نظر امتیاز را بازمحاسبه می‌کند — ۰ → ۱
✓ رد نظر امتیاز را پس می‌گیرد
```

## تأیید کافه‌ی ثبت‌شده ← `draft` نه `published`

داده‌ی کاربر ناقص است (معمولاً فقط نام و آدرس) و انتشار فوری یعنی یک صفحه‌ی
خالی در سایت. ادمین بعد از کامل‌کردن، دستی منتشرش می‌کند.

## چطور تست شد

`npm run admin:smoke` — **۳۳ بررسی، همه سبز**. نمونه‌ها:

```
✓ ربات جدا شمرده می‌شود
✓ حساب کافه بدون شماره ساخته می‌شود — ادمین شماره‌ی جعلی نمی‌سازد
✓ رمز صادرشده کار می‌کند · رمز موقت علامت خورده
✓ رمز قبلی باطل شد
✓ کاربر عادی رمز دائمی می‌گیرد
✓ نظر تأییدنشده امتیاز را عوض نمی‌کند
✓ تکراری رد نمی‌شود، علامت می‌خورد — احتمال تکراری با «مجنون لانژ»
✓ سلامت داده — ۳۳۱ مکان · ۷۳ بی‌مختصات · ۵ فروشگاه
```

ثبت بازدید هم روی سرور واقعی بررسی شد:

```
POST /api/track × 5 → 204
page_view: device=mobile · place_id=87 برای /cafe/jan-majnoon-lounge · referrer ثبت شد
place.view_count: مجنون لانژ ۱ · آو کامپلکس ۱
```

و `/admin` با نشست واقعی: ۲۰۰ · ۷۶KB · همه‌ی شش تب.

**`npx tsc --noEmit` روی کل پروژه: صفر خطا.**

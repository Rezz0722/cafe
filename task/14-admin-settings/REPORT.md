# تسک ۱۴ — تنظیمات سایت و امکانات پنل ادمین

**خواسته:** «تنظیمات کلی مثل ساعت زمانی و یک لیست کامل امکانات رو که لازمه و
برای این که بعداً نیاز به برنامه‌نویسی نباشه ببر سمت پنل ادمین. خودت راجبش فکر
کن که پنل ادمین چه امکاناتی لازم داره که بعداً نیاز به برنامه‌نویسی نداشته
باشیم، همونا رو لیست کن.»

دو خروجی دارد:

1. **[`CAPABILITIES.md`](./CAPABILITIES.md)** — فهرست خواسته‌شده: چه چیزی امروز
   از پنل قابل انجام است، چه چیزی نه (با اولویت)، و چه چیزی **عمداً** نباید
   تنظیم شود.
2. همین گزارش — چه چیزی ساخته و وصل شد، و چه چیزی در راه پیدا شد.

## ۱. چه چیزی ساخته شد

### رجیستری تنظیمات — `src/core/settings/`

| فایل | کار |

**قاعده‌ی «تعریف در کد، مقدار در دیتابیس»:** کلیدی که در جدول `setting` ردیف
نداشته باشد پیش‌فرضِ کد را می‌گیرد. یعنی جدول فقط تفاوت‌ها را نگه می‌دارد،
سایت روی دیتابیس خالی بالا می‌آید، و «بازگردانی به پیش‌فرض» = پاک‌کردن ردیف.

### پنل

- **تب تنظیمات** (`SettingsPanel.tsx`) — یک فرم برای هر گروه، خطای هر فیلد زیر
  همان فیلد، نشانِ «تغییر داده شده» روی کلیدهایی که از پیش‌فرض فاصله گرفته‌اند،
  و هشدارِ «بعد از این تغییر باید بازمحاسبه کنی» روی تنظیم‌هایی که به ستون
  مشتق دست می‌زنند.

  ترمینال می‌شد، به‌علاوه‌ی فهرستِ صریحِ کارهایی که **عمداً** دکمه ندارند.

### ماژول‌های هسته: پارامتری، با همان پیش‌فرض

هیچ ماژول هسته‌ای `getSettings()` صدا نمی‌زند. همه عدد را **پارامتر** می‌گیرند
با پیش‌فرضِ قبلی، و صفحه/اکشن مقدار را از تنظیمات پاس می‌دهد.

دلیل: `openNow.ts` و `normalize.ts` و `otp.ts` خالص‌اند و ۲۱۲ تست رویشان
سوار است. اگر دیتابیس بخوانند، هیچ‌کدام از آن تست‌ها بدون MySQL اجرا نمی‌شود.
اثر جانبی‌اش هم این است که اگر جدول تنظیمات از دسترس خارج شود، سایت با
پیش‌فرض‌های امن کار می‌کند نه با صفر.

## ۲. سه تله که سر راه بسته شد

### ۲.۱ تنظیمی که سایت را قفل می‌کند

«ورود با رمز» و «ورود با کد پیامکی» هر دو سوئیچ دارند. خاموش‌کردن هر دو،
**همه** را — از جمله خودِ ادمین — بیرون می‌گذارد و راه برگشتی نمی‌ماند.
`validateSettings` این ترکیب را رد می‌کند و **هیچ فیلدی** از آن فرم ذخیره
نمی‌شود.

همان منطق برای حالت تعمیر: دروازه‌اش عمداً روی `/auth`، `/admin`، `/profile` و
پنل کافه اعمال **نمی‌شود**. اگر می‌شد، کسی که روشنش کرده راهی برای
خاموش‌کردنش نداشت.

### ۲.۲ چک‌باکسِ خاموش در `FormData` وجود ندارد

نه با `false` — اصلاً نیست. سروری که فقط کلیدهای موجود را ببیند، **هرگز**
نمی‌تواند سوئیچی را خاموش کند و این باگ هیچ خطایی نمی‌دهد؛ فقط ذخیره «موفق»
می‌شود و مقدار عوض نمی‌شود.

راه‌حل: فرم برای هر فیلد بولی یک فیلد پنهان با نام `__bool` و مقدارِ همان کلید
هم می‌فرستد. اکشن اول همه‌ی `__bool`ها را `false` می‌گذارد و بعد روی مقادیر
واقعیِ فرم می‌رود. تستِ `parseSettingValue` هم `'on'`، `'true'`، `false` و
رشته‌ی خالی را جدا می‌سنجد.

### ۲.۳ سرریزِ `entity_id` — ذخیره‌ی تنظیمات را می‌ترکاند

نسخه‌ی اول، نام کلیدهای تغییریافته را با کاما در `audit_log.entity_id` می‌ریخت.
آن ستون `varchar(64)` و **ایندکس‌شده** است. ذخیره‌ی یک گروهِ شش‌فیلدی از ۶۴
کاراکتر می‌گذشت و کل تراکنش می‌افتاد:

```
Data too long for column 'entity_id' at row 1   (ER_DATA_TOO_LONG)
```

یعنی «ذخیره‌ی چند تنظیم با هم» — که کارِ عادیِ این پنل است — کار نمی‌کرد.
`settings-smoke.ts` در **اولین اجرا** گرفتش. فهرست کامل الان در
`before`/`after` (که `json`اند) می‌رود و `entity_id` یا نام همان یک کلید است یا
شکلِ «N keys».

## ۳. تصمیم‌هایی که ممکن است سؤال ایجاد کنند

**`smsDevMode` بر `AUTH_DEV_MODE` مقدم است.** کسی که پنل ادمین دارد باید
بتواند بدون ری‌دیپلوی سایت را از حالت توسعه بیرون بیاورد. پیش‌فرضِ این تنظیم
همان پیش‌فرض env است، پس رفتار فعلی عوض نشده.

**`/api/map/style` از `force-static` به `force-dynamic` رفت.** زومِ نمایش
ساختمان الان از دیتابیس می‌آید؛ استایلِ استاتیک یعنی تغییرِ آن تنظیم تا
ری‌دیپلوی بعدی دیده نمی‌شود. کشِ یک‌ساعته‌ی HTTP همان صرفه را دارد بدون این تله.

**تأیید خودکار نظر، رول‌آپ امتیاز را هم به‌روز می‌کند.** با
`reviewsRequireApproval = false`، نظرِ تازه مستقیم `approved` می‌شود؛ پس
`recalcPlaceRating` باید همان‌جا صدا زده شود، وگرنه امتیاز مکان یک نظر عقب
می‌ماند. برای ویرایش هم شرط دو طرفه شد: نظری که از تأییدشده به صف برگشت هم
باید از میانگین کم شود.

**پیام «بعد از بررسی منتشر می‌شود» شرطی شد.** با تأیید خودکار، آن جمله دروغ
است و کاربر بی‌دلیل منتظر می‌ماند.

**ربات‌ها دیگر پیش‌فرضاً در `page_view` ثبت نمی‌شوند.** قبلاً ردیفشان نوشته
می‌شد و فقط از `place.view_count` بیرون می‌ماند؛ نتیجه این بود که جدول خام با
خزنده‌ها پر می‌شد و هر پرس‌وجوی آماری باید `device <> 'bot'` را یادش می‌ماند.
با تنظیم `countBotsInStats` قابل برگشت است.

| بررسی | نتیجه |

| `npm test` | **۲۱۲ تست، همه موفق** (۱۸۵ قبلی + ۲۷ تست تنظیمات) |
| `npx tsc --noEmit` | پاک |
| `npm run build` | موفق — ۳۶ صفحه |
| `npm run db:verify` | ساختار سالم · ۳۳۱ مکان · ۱۹٬۳۸۶ آیتم · ۱۴٬۴۸۰ تصویر |
| `npm run settings:smoke` | **۲۲ بررسی** — نوعِ داده در ستون `json`، upsert، کش، اعتبارسنجی، بازگردانی |
| `npm run settings:effect` | **۱۸ بررسی** — تنظیم عوض شد، صفحه‌ی واقعی دیدش |
| `npm run pages:smoke` | ۲۱ صفحه، همه سالم |
| `auth` / `manage` / `admin` / `map` / `query` smoke | همه موفق |

### دو دود-تست تازه

**`settings:smoke`** چیزهایی را می‌سنجد که فقط با MySQL واقعی معلوم می‌شوند:
آیا ستون `json` بولی را بولی برمی‌گرداند یا `1`؟ آیا upsert ردیف دوم نمی‌سازد؟
آیا ردیفِ خرابِ دستی (`searchPageSize = "بیست"`) نادیده گرفته می‌شود؟ آیا
اعتبارسنجی بین‌فیلدی **قبل** از نوشتن جلو را می‌گیرد؟ در پایان وضعیت اولیه را
برمی‌گرداند.

**`settings:effect`** فاصله‌ی «ذخیره شد» تا «سایت دیدش» را می‌سنجد — همان‌جایی
که باگ‌های «تنظیم گذاشتم ولی اثری نداشت» زندگی می‌کنند. تنظیمات را عوض می‌کند،
از **بیرون** به سرور production درخواست می‌زند و بررسی می‌کند:

```
✓ عنوان صفحه از تنظیمات ساخته شد
✓ بنر اعلان رندر شد
✓ سقف قیمتِ تازه به کلاینت رسید — 123000
✓ تعداد صفحه‌ها با اندازه‌ی تازه حساب شد — صفحه ۱ از ۵۵
✓ سرویس حذف‌شده دیگر نیست            (نشان از فهرست بیرون رفت)
✓ زومِ ساختمان از تنظیمات آمد — minzoom=17
✓ صفحه‌ی محله هم بسته شد (پیش‌تولید استاتیک آن را دور نمی‌زند)
✓ ولی صفحه‌ی ورود باز ماند
```

آن یکی‌مانده‌به‌آخر مهم بود: `/mashhad/[district]` در build پیش‌تولید می‌شود و
این احتمال جدی بود که حالت تعمیر آن را دور بزند. تست نشان داد نمی‌زند.

## ۵. جمع‌بندی

۶۵ عددی که تا دیروز در ۱۵ فایل هاردکد بودند، امروز در پنل ادمین‌اند — با
اعتبارسنجی، لاگ تغییرات، بازگردانی به پیش‌فرض، و دود-تستی که ثابت می‌کند
تغییرشان به صفحه‌ی واقعی می‌رسد.

فهرست آنچه **هنوز** لازم است در [`CAPABILITIES.md`](./CAPABILITIES.md) بخش ۳
آمده. مهم‌ترینش یکی است: **ویرایش کامل یک مجموعه از پنل ادمین**. منطقش از قبل
هست (پنل کافه)، فقط راه ورودِ نوشتنی‌اش از ادمین ساخته نشده.

# تسک ۱۱ — پنل کافه‌دار ✅

## چه چیزی ساخته شد

پنل `/admin/venue` روی **داده‌ی واقعی MySQL** بازنویسی شد. پنل قبلی روی
`adminSeed.ts` (داده‌ی ساختگی) کار می‌کرد و هیچ چیزی را واقعاً ذخیره نمی‌کرد.

پنج تب، بر اساس کاری که کافه‌دار **واقعاً** انجام می‌دهد:

| تب | چه کاری |
| --- | --- |
| نمای کلی | آمار + **فهرست کارهای باقی‌مانده** با لینک مستقیم به رفعشان |
| اطلاعات | نام، درباره، آدرس، شماره‌ها، اینستاگرام، مختصات |
| ساعت کاری | ۷ روز × ۲ شیفت + تعطیل |
| منو و قیمت | **تغییر دسته‌ای درصدی** + ویرایش تک‌آیتم |
| نظرها | دیدن همه (با وضعیت) + پاسخ |

## سه تصمیم که پنل را کاربردی می‌کند

### ۱. تغییر دسته‌ای قیمت، در دسترس‌ترین جای منو

با تورم ایران، کافه‌دار هر چند ماه **کل** منو را چند درصد بالا می‌برد. ویرایش
تک‌تکِ ۲۸۷ آیتم یعنی این کار هرگز انجام نمی‌شود و قیمت‌های سایت بیات می‌مانند
— بدترین حالت برای اعتماد کاربر.

یک عدد درصد، یک دکمه. نتیجه **به هزار تومان گرد می‌شود**: قیمتِ ۳۱۷٬۴۲۰ تومان
در منو معنی ندارد. بازه‌ی مجاز ‎-۹۰ تا ۲۰۰ درصد، تا یک صفرِ اضافه کل منو را
نابود نکند.

### ۲. «چه چیزی می‌تواند بهتر شود» به‌جای نمودار تزئینی

نمای کلی، به‌جای یک نمودار، **فهرست کارِ واقعی** می‌دهد و هر مورد لینک
مستقیم به تبِ رفعش دارد:

- مختصات ثبت نشده → «بدون آن، مجموعه‌تان روی نقشه و در نزدیک من دیده نمی‌شود»
- ساعت کاری ثبت نشده → «پرتکرارترین سؤال کاربران»
- قیمت X آیتم بیش از سه ماه به‌روز نشده
- درباره خالی · شماره تماس ندارد

اگر همه کامل بود: «پروفایل کامل است. ✓»

### ۳. `crossesMidnight` محاسبه می‌شود، نه پرسیده

اگر ساعت بستن ≤ ساعت باز شدن باشد، قطعاً از نیمه‌شب گذشته. پرسیدنش از
کافه‌دار یک سؤال گیج‌کننده و یک منبع خطاست. تست ثابت می‌کند ۱۶:۰۰ تا ۰۰:۳۰
خودکار به‌عنوان گذر از نیمه‌شب ثبت می‌شود.

## امنیت: مالکیت روی **آیتم** بررسی می‌شود، نه روی فرم

مهم‌ترین بند این تسک. `saveMenuItemAction` شناسه‌ی مکان را **از خودِ آیتم**
می‌خواند، نه از `placeId` که در فرم آمده:

```ts
const [item] = await db.select({ placeId: menuItem.placeId })...
const access = await requirePlaceAccess(item.placeId)
```

بدون این، کافه‌داری که شناسه‌ی مکان را در فرم عوض کند می‌توانست منوی کافه‌ی
دیگری را ویرایش کند — و این نوع باگ در هیچ لاگی دیده نمی‌شود.

همین قاعده برای پاسخ به نظر هم اعمال شده: `placeId` از خودِ `review` خوانده
می‌شود.

## سه چیز که با هر نوشتن **با هم** انجام می‌شوند

`src/core/places/manage.ts` تنها جایی است که روی مکان می‌نویسد، چون هر تغییر
باید سه کار را با هم بکند:

1. **نوشتن داده**
2. **بازمحاسبه‌ی مقادیر مشتق** (`refreshPlaceDerived`) — رده‌ی قیمت، کمینه،
   میانه، بیشینه، امتیاز کیفیت. بدونش، کافه‌داری که قیمت‌ها را دو برابر
   می‌کند در فیلتر «اقتصادی» باقی می‌ماند.
3. **ثبت رد پا** (`audit_log`) با `before` **و** `after` — برگرداندن یک
   ویرایش اشتباه بدون دانستن مقدار قبلی ممکن نیست.

اگر هر صفحه‌ای خودش می‌نوشت، یکی از این سه فراموش می‌شد.

## دسترسی

| نقش | چه می‌بیند |
| --- | --- |
| مالک | فقط کافه‌های خودش (از `user_place_role`) |
| مالکِ چندکافه | انتخابگر مجموعه در سرصفحه |
| مدیر | هر کافه‌ای با `?place=<id>`؛ **بدون پارامتر، فهرست انتخاب** |
| «مشاهده به‌عنوان» | فقط‌خواندنی — دکمه‌های ذخیره حذف می‌شوند |

ادمین بدون پارامتر، یک کافه‌ی تصادفی نمی‌بیند بلکه فهرست انتخاب: باز شدنِ
پنلِ کافه‌ای که ادمین انتخابش نکرده، خطرِ ویرایش اشتباه دارد.

در حالت «مشاهده به‌عنوان» دکمه‌ها **حذف** می‌شوند، نه اینکه بزنی و خطا
بگیری — نمایشِ دکمه‌ای که کار نمی‌کند بدتر از نبودنش است.

## چطور تست شد

`npm run manage:smoke` روی کافه‌ی واقعی «مجنون لانژ» (۱۶ دسته، ۹۹ آیتم
قیمت‌دار) — **۲۰ بررسی، همه سبز**:

```
✓ رد پا در audit_log ثبت شد
✓ شیفت شکسته ذخیره شد — ۲ شیفت شنبه
✓ گذر از نیمه‌شب خودکار تشخیص داده شد — ۱۶:۰۰ تا ۰۰:۳۰
✓ زمان تأیید قیمت ثبت شد
✓ قیمت خالی → NULL و «قیمت روز»   ← نه صفر
✓ تغییر دسته‌ای قیمت — ۹۹ آیتم
✓ میانه‌ی قیمت بازمحاسبه شد — ۹۴۰٬۰۰۰ → ۱٬۰۳۴٬۰۰۰
✓ قیمت‌ها به هزار تومان گرد شدند
✓ درصد صفر رد می‌شود · درصد خارج از بازه رد می‌شود
✓ اطلاعات و ساعت کاری برگردانده شد
```

تست در پایان همه‌چیز را برمی‌گرداند (میانه دقیقاً به ۹۴۰٬۰۰۰ برگشت) و رد
پای خودش را از `audit_log` پاک می‌کند تا لاگ واقعی شلوغ نشود.

صفحه هم با نشست واقعی بررسی شد:

```
/admin/venue            → ۲۰۰ · فهرست انتخاب مجموعه (ادمین)
/admin/venue?place=87   → ۲۰۰ · مجنون لانژ · همه‌ی تب‌ها
```

## یک باگ ابزاری که پیدا شد

`tsc` با **out-of-memory** می‌ترکید. علتش `sql.join` روی یک آرایه‌ی
نگاشت‌شده بود که استنتاج تایپ را منفجر می‌کرد. با `inArray` جایگزین شد —
هم درست‌تر و هم قابل کامپایل.

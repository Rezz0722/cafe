# KuCafe P1-01 — حفاظت دادهٔ ویرایش‌شده در پنل در برابر اسکرپر

تاریخ: ۱۲ اکتبر ۲۰۲۶ · Branch: `feat/p1-01-owner-data-protection` · PR مستقل: [#65](https://github.com/Rezz0722/cafe/pull/65). **بدون Merge، Migration یا Deploy روی Production.**

## شواهد و علت ریشه‌ای

- `scripts/topmenu-sync.ts` پیش‌تر در Apply، آیتمِ دارای `source_id` را با فیلدهای منبع جایگزین و آیتم غایب را آرشیو می‌کرد؛ Match دسته بر پایهٔ نام نمایشی بود.
- `src/core/places/manage.ts` ویرایش پنل را Audit می‌کرد اما به Sync نمی‌گفت کدام فیلد آگاهانه تغییر کرده است. وقوع خسارت واقعی در Production از این کد ثابت نشد.
- مسیرهای بررسی‌شده: ویرایش تک‌آیتم/دسته، عکس، ترتیب، آرشیو، سایز، موجودی گروهی، تغییر قیمت گروهیِ فعلی و مسیر قدیمی قیمت، Admin scope، TopMenu Preview/Apply، `import-lipar.ts` و بازسازی facet/dish.

## تغییرات اجراشده

- طراحی پیش از Migration در `docs/KUCAFE_P1_01_DESIGN_FA.md` ثبت شد.
- Migration افزایشی `drizzle/0015_menu_source_overrides.sql`: دو جدول نشان فیلدی با FK و `menu_section.source_name`. هیچ رکورد قدیمی خودکار owner-verified نمی‌شود.
- ویرایش‌های واقعاً تغییرکرده در مسیرهای پنل با منشأ انسانی و actor ثبت می‌شوند؛ قیمت پایهٔ آیتم سایزدار از منبع بازنویسی نمی‌شود. آیتم دستیِ بدون `source_id` همچنان حفظ می‌شود.
- Preview تعداد/جزئیات اختلاف محافظت‌شده و تغییرات دسته را نشان می‌دهد؛ Apply دوباره از DB فعلی Merge می‌کند و فقط فیلدهای آزاد را وارد می‌کند. کنترل بعد از Apply مقدار **مؤثر** را می‌سنجد، نه برابری مطلق با منبع.
- دستهٔ تغییرنام‌یافتهٔ مالک با `source_name` پایدار می‌ماند. تغییر نام منبع فقط با تطبیق یکتای آیتم‌های وارداتی به دستهٔ قبلی وصل می‌شود؛ حالت مبهم دادهٔ مالک را بازنویسی نمی‌کند.
- Apply پیش از خواندن Snapshot، فقط منوی کافه‌های انتخاب‌شده را قفل می‌کند؛ ترانزاکشن، بکاپ پیش از Apply و Audit خلاصهٔ اختلاف‌های محافظت‌شده حفظ شده‌اند.
- ادمین می‌تواند نشان یک فیلد را با دلیل و تأیید صریح بردارد؛ این کار مقدار فعلی را تغییر نمی‌دهد و فقط Sync بعدی می‌تواند آن را از منبع بگیرد. این عملیات Audit دارد و View-as/غیرادمین را گارد موجود رد می‌کند.
- Import دستی لیپار در صورت وجود نشان ویرایش انسانی برای شعبه، پیش از بازنویسی با خطای روشن متوقف می‌شود؛ این Import هنوز Merge فیلدی نیست.
- CI یک آزمون DB واقعی جدید روی MariaDB موقت اجرا می‌کند.

## Backup / Rollback / ایمنی انتشار

قبل از Apply، `scripts/backup-db.mjs` همچنان بکاپ فشرده می‌سازد و شکست بکاپ Apply را متوقف می‌کند. شکست داخل تراکنش دادهٔ قبلی را نگه می‌دارد. Rollback کد به commit قبلی باید **قبل از** اجرای `drizzle/0015_menu_source_overrides.rollback.sql` انجام شود. Drop جدول‌ها نشان‌های تازه را نابود می‌کند؛ ابتدا Export/بکاپ آن‌ها لازم است. هیچ Migration روی DB اصلی اجرا نشده است.

## ریسک و Gate باقی‌مانده

1. ویرایش‌های تاریخیِ پیش از Migration در جدول نشان‌ها نیستند. قبل از اولین Sync بعد از استقرار، Audit تاریخی کافه‌های دارای ویرایش پنل باید دستی بررسی و تعارض‌ها تصمیم‌گیری شود؛ آن‌ها خودکار به‌عنوان owner-verified علامت نمی‌خورند.
2. قفل‌گذاری هم‌زمانی با کد و DB واقعی آزموده شده، اما سناریوی رقابت هم‌زمان دو نویسنده و بار کامل ۴۲هزار آیتم روی Production آزمایش نشده است. اولین انتشار باید انتخاب محدود، بکاپ معتبر و پایش لاگ داشته باشد.
3. UI رفع تعارض فعلاً برای ادمین است؛ Owner/Manager می‌توانند ویرایششان را ثبت کنند، اما آزادسازی مستقیم Override از پنلشان در این PR ارائه نمی‌شود. تصمیم اختلاف انسانی بر عهدهٔ ادمین است.
4. SEO/ranking گوگل و اثر واقعی کش Production بدون Deploy قابل تأیید نیست؛ Build و SSR محلی جای آن نیستند.
5. دو کافهٔ پایلوت، Entitlement پولی و سیاست retention همچنان طبق گزارش P0 وابسته به مالک‌اند.
